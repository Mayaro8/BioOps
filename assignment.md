# BioOps — мультиагентная система для эксплуатации биоинформатических пайплайнов

Задание на летнюю практику 2026.

## 1. Контекст

В Genotek биоинформатическая обработка устроена как пайплайн `pipeline-v3.0` — последовательность шагов, каждый из которых живёт в своём репозитории, запускается в Kubernetes, использует базы данных (в т.ч. ClickHouse), очереди и облачные функции. Обработка идёт батчами.

Сейчас эксплуатация пайплайна требует ручной работы: разработчик/дежурный сам ходит в k8s, смотрит логи, считает стоимость подов и VM, перезапускает упавшие задачи, отвечает на вопросы коллег «а что сейчас происходит с батчом N» и «как устроен такой-то шаг».

**Цель практики** — спроектировать и реализовать **BioOps**: мультиагентную систему, которая снимает рутину с команды. Она отвечает на вопросы о пайплайне, делает ревью, следит за здоровьем инфраструктуры, управляет запусками и ведёт прозрачную картину статусов обработки.

## 2. Что такое BioOps (общая идея)

BioOps — это не один большой бот, а **набор специализированных агентов** под единым оркестратором. Пользователь (инженер, биоинформатик, дежурный) общается с системой в чате (Telegram/Bitrix) или получает от неё автоматические алерты и отчёты.

```text
                 ┌─────────────────────────┐
   пользователь  │      Оркестратор        │  маршрутизация запроса
   ───────────►  │  (router / supervisor)  │  к нужному агенту
                 └────────────┬────────────┘
                              │
   ┌──────┬──────┬───┴──┬──────┬──────┬──────┐
   ▼      ▼      ▼      ▼      ▼      ▼      ▼
 Know-  Review Cluster Submit Infra/ Batch  Storage
 ledge  Agent  Health  Master Cost   Status Agent
 Agent         Agent   Agent  Mon.   Agent
   │      │      │      │      │      │      │
   └──────┴──────┴──┬───┴──────┴──────┴──────┘
                    ▼
                   Инструменты (tools):
        k8s API · GitHub API · Yandex Cloud API · ClickHouse ·
        очереди · Cloud Functions · Object Storage (S3) ·
        векторная БД (доки) · БД статусов
```

Ключевые принципы:
- **Агент = роль + набор инструментов.** Каждый агент умеет вызывать ограниченный набор инструментов (tools) и отвечает за свою зону.
- **Два режима работы:** реактивный (отвечает на запрос пользователя) и проактивный (периодические health-check'и по расписанию + алерты).
- **Любой алерт/отчёт — короткий и действенный:** что случилось, где, насколько критично, что предлагается сделать.

## 3. Глоссарий

| Термин | Значение |
|---|---|
| `pipeline-v3.0` | Биоинформатический пайплайн — последовательность шагов обработки. |
| Шаг (step) | Отдельная стадия пайплайна, живёт в своём git-репозитории. |
| Батч (batch) | Партия образцов, проходящая через пайплайн. |
| Submit master | Сервис/процесс, который по конфигу запускает обработку (сабмитит задачи). |
| Под (pod) | Единица запуска в Kubernetes. |
| CH | ClickHouse — аналитическая БД. |
| Compute Cloud | Сервис виртуальных машин (Yandex Cloud). |
| Cloud Functions | Бессерверные облачные функции (Yandex Cloud). |
| Object Storage (S3) | Объектное хранилище; данные лежат в бакетах (напр. `genotek-testing`). |
| `genotek-testing` | Бакет в Object Storage с данными/артефактами обработки. |
| MR / PR | Merge / Pull Request. |

## 4. Функциональные требования (эпики)

Требования сгруппированы в эпики. Внутри каждого — пользовательские сценарии. Приоритет (P0/P1/P2) задаёт порядок реализации, см. раздел «Этапы».

### Эпик A. Knowledge Agent — экспертиза по пайплайну `P0`

Агент-«документация», который знает устройство пайплайна.

- **A1.** Рассказывает в общих чертах про шаги пайплайна `pipeline-v3.0`: какие есть шаги, в каком порядке идут, за что отвечают.
- **A2.** Отвечает на вопросы про конкретный шаг и обязательно прикрепляет ссылку на документацию и репозиторий шага:
  - входные данные;
  - выходные данные;
  - логика работы;
  - параметры запуска.
- **A3.** Источник знаний — индексированная документация и репозитории шагов (RAG: векторная БД + ссылки на первоисточники). Ответ всегда содержит ссылку-первоисточник.

### Эпик B. Review Agent — ревью кода шагов `P1`

- **B1.** По запросу делает ревью конкретного шага по его репозиторию.
- **B2.** По запросу проверяет открытые MR в репозитории шага.
- **B3.** Делает ревью по переданной ссылке на конкретный MR.
- **B4.** Результат ревью — структурированный комментарий: найденные проблемы, риски, замечания по стилю/логике, предложения. Без «воды».

### Эпик C. Cluster Health Agent — здоровье k8s-кластеров `P0`

Проактивный + реактивный.

- **C1.** Периодический health-check биоинформатических k8s-кластеров.
- **C2.** Анализ логов на ошибки.
- **C3.** Отвечает, какой шаг пайплайна сейчас запущен.
- **C4.** Детализация: статусы подов, их стоимость, предположительный ETA до завершения текущего шага.
- **C5.** Если что-то запущено — присылает короткий периодический отчёт о состоянии.

### Эпик D. Submit Master Agent — запуск и мониторинг обработки `P1`

- **D1.** Генерирует конфиг для submit master.
- **D2.** Запускает submit master.
- **D3.** Мониторит submit master: логи, ошибки, статусы, стоимость, ETA до завершения.
- **D4.** Присылает отчёт по упавшим подам.
- **D5.** По запросу перезапускает упавшие поды.

### Эпик E. Infra & Cost Monitoring — мониторинг инфраструктуры `P1`

Несколько проактивных мониторов с алертами.

- **E1. VM в Compute Cloud.** Периодическая проверка стоимости VM. Формирует **alert**, если «дорогая» VM (дороже 50 000 ₽/мес **или** с GPU) включена дольше 3 часов.
- **E2. Хосты БД пайплайнов.** Периодический health-check: CPU, RAM, мутации в ClickHouse. Алерт при подозрительных значениях.
- **E3. Очереди.** Периодический health-check: если очередь долго не разгребается или разгребается слишком медленно — алерт.
- **E4. Облачные функции.** Периодический health-check биоинформатических Cloud Functions: алерт при критическом росте нагрузки или ошибках в логах.

### Эпик F. Batch Status Agent — статусы обработки батчей `P1`

- **F1.** Наполняет таблицу в БД со статусами обработки батчей.
- **F2.** Синхронизирует таблицу с Google-документом (двусторонне или в одну сторону — уточнить с ментором).
- **F3.** Отвечает на вопросы по статусу любого батча.

### Эпик G. Storage / Bucket Agent — консультации по бакету `P1`

Агент, который знает структуру объектного хранилища и умеет считать по нему агрегаты.

- **G1.** Консультирует по структуре бакета `genotek-testing`: какие префиксы/папки есть, что где лежит, как организованы данные.
- **G2.** Отвечает на агрегирующие вопросы по содержимому, например: суммарный размер всех `.bam`-файлов, количество объектов по типу/префиксу, размер конкретной папки.
- **G3.** Источник данных — S3 inventory / листинг бакета. Для тяжёлых агрегатов опираться на инвентаризацию, а не на полный обход «вживую» при каждом запросе.
- **G4.** В ответе указывает, на какой момент актуальны данные (дата инвентаризации/листинга).

## 5. Нефункциональные требования

- **Расширяемость.** Добавить новый агент/инструмент/монитор — без переписывания ядра.
- **Конфигурируемость.** Пороги алертов (50 000 ₽, 3 часа, скорость очереди и т.п.), расписания, список кластеров/репозиториев — в конфиге, не в коде.
- **Наблюдаемость.** Логирование действий агентов; видно, какой агент что вызвал и почему.
- **Безопасность.** Секреты (токены k8s, GitHub, облака) — через переменные окружения/секрет-менеджер, не в коде. Действия с побочными эффектами (перезапуск подов, запуск submit master) — только по явному подтверждению.
- **Стоимость LLM.** Разумное использование токенов: кэширование, краткие промпты, RAG вместо «загрузить всё в контекст».

## 6. Рекомендуемый стек

> Финальный выбор — за студентом и ментором. Ниже отправная точка.

- **Язык:** Python 3.11+.
- **Оркестрация агентов:** LangGraph / LangChain или аналог с tool-calling.
- **LLM:** по согласованию с ментором (что доступно в контуре).
- **RAG:** векторная БД (Qdrant / pgvector / Chroma) для документации шагов.
- **Интеграции:** Kubernetes Python client, GitHub API (PyGithub), Yandex Cloud SDK/CLI, ClickHouse client, клиент очередей, S3-клиент (boto3) + S3 inventory.
- **Интерфейс:** Telegram/Bitrix-бот + webhook для алертов.
- **Планировщик:** APScheduler / cron / k8s CronJob для периодических проверок.
- **Хранилище статусов:** реляционная БД + синхронизация с Google Sheets API.

- Поднять скелет проекта: оркестратор + один «эхо»-агент, конфиги, логирование.

### Этап 1. MVP — знания + здоровье кластера (недели 2–3) `P0`
- Эпик A (Knowledge Agent) целиком.
- Эпик C (Cluster Health Agent): C1–C5.

### Этап 2. Запуск и управление обработкой (недели 4–5) `P1`

> Сроки ориентировочные — корректируются с ментором под реальную длительность практики.

## 8. Критерии приёмки (Definition of Done)

Фича считается готовой, когда:
- сценарий из эпика воспроизводится в демо на реальных (или максимально приближенных) данных;
- есть конфиг для всех порогов/расписаний, никакой «магии» в коде;
- действия с побочными эффектами требуют подтверждения и логируются;
- алерты/отчёты краткие и содержат «что случилось / где / критичность / что делать»;
- код прошёл ревью ментора, есть базовые тесты на ключевую логику;
- обновлён README/доки: как запустить, как настроить, как добавить новый агент.
